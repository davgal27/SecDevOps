	\section{Task 1: Reliable and Robust Application Platforms}
	
	\subsection{Task 1(a)}
	
	\textbf{CloudNative Operator deployment}
	
	The original single PostgreSQL setup was replaced with a CloudNativePG-managed PostgreSQL cluster. The CloudNativePG Helm repository was added, and the CNPG operator was installed in the \texttt{cnpg-system} namespace using Helm, using appropriate documentation \cite{cnpgdownload} as reference.

	
	\textbf{Cluster bootstrap}
	
	The PostgreSQL cluster was created using \texttt{task1a/yamls/cnpg\_cluster.yaml}. This manifest created the Kubernetes secret \texttt{app-secret} and bootstrapped the \texttt{fnd-db} cluster with the \texttt{ordersdb} database owned by \texttt{clusteruser}. Reference for how to perform this step was obtained from cloudnative-pg.io documentation \cite{cnpgbootstrap}.
	
	
	\textbf{Read-write/read-only split}
	
	CloudNativePG exposed the required split through separate Kubernetes services. The \texttt{fnd-db-rw} service targets the current primary instance and is used for read-write traffic. The \texttt{fnd-db-ro} service targets replica instances and is used for read-only traffic.
	
	The cluster was configured with \texttt{instances:3}. For the read-write/read-only split, 2 instances would have been sufficient, since this would provide one primary instance and one replica. Although the additional replica was not strictly required for the task, it improved the final setup by increasing the capacity available for read-only traffic.
	
	\textbf{Resource verification}
	
	Correct Kubernetes resource creation and pod deployment was confirmed using \texttt{kubectl}. All commands used can be found in the \textbf{task1a readme.txt}
	
	\subsection{Task 1(b)}
	
	\textbf{Preparing the Repository}
	
	After splitting the codebase into respective versions, one for read-write, and one for read-only, both versions were prepared to perform their respective tasks. Naturally most configuration was applied to the read-only version of the app, as it is the version which required inhibition of previously available features. 
	
	Changes made to the read only codebase include:
	\begin{itemize}
		\item Applying of a RepositoryRestConfigurer to block non-GET requests (file at \texttt{app-ro/src/}\\\texttt{main/java/com/example/foodndeliv/config/SpringDataRestCustomization.java}). \\ Reference code was used from 2nd set of notes: Reliable Application Platforms.pdf, from pages 124-125.
		
		\item Modifying controllers and services in the source code to block any mappings (such as put and post) exposed which may allow non-GET requests, as well as comment out any keycloak-dependent code.
		
		\item Disabling of keycloak config files, as they were not needed for this task
		
	\end{itemize}
	
	Changes made to both repositories:
	\begin{itemize}
		\item Modifying the docker files accordingly
		
		\item Adding an exception handler for HTTP methods, which shows specific errors for when a method is not supported (eg, POST on a read-only service).
		
		\item Modifying application.properites. Most importantly \texttt{spring.jpa.hibernate.ddl-auto=\_\_}. This was set as \texttt{=update} for the first building of the RW app, and then as \texttt{=none} for the second rebuilding, for reasons explained in the \textbf{Schema Setup} section below.
	\end{itemize}
	
	\textbf{Connecting the services to the databases}
	
	The \texttt{fnd-rw} deployment sets \texttt{DB\_HOST=fnd-db-rw}, while the \texttt{fnd-ro} deployment sets \texttt{DB\_HOST=} \texttt{fnd-db-ro}.
	
	The deployments and services were created using \texttt{yamls/rw-deployment.yaml}, \texttt{yamls/ro-deplo-} \texttt{yment.yaml}, \texttt{yamls/rw-service.yaml}, and \texttt{yamls/ro-service.yaml}. The resulting services were \texttt{fnd-rw} and \texttt{fnd-ro}.. Both deployments use the credentials defined in \texttt{yamls/db-secret.yaml}. The yaml file configuration was inspired from the kubernetes documentation\cite{Connecting applications with services kubernetes} \cite{Define Environment Variables for a Container} \cite{Distribute Credentials Securely Using Secrets}

	
	\textbf{Deployment}
	
	Both applications were built as separate Maven projects and Docker images. The read-write image was pushed as \texttt{davegalea/foodndeliv-rw:task1b}, and the read-only image was pushed as \texttt{davegalea/foodndeliv-ro:task1b}.
	
	\textbf{Schema setup}
	
	For the first read-write deployment, \texttt{spring.jpa.hibernate.ddl-auto=update} was used so that  the database schema could be create. After this, the read-write application was rebuilt with \texttt{spring.jpa.hibernate.ddl-auto=none}. The read-only version also used \texttt{ddl-auto=none}, since it should not create or modify the schema.
	
	\textbf{Testing and verification}
	
	The services were exposed locally using port forwarding:
	
	\begin{verbatim}
		kubectl port-forward svc/fnd-ro 8080:8080 (for read only)
		kubectl port-forward svc/fnd-rw 8081:8080 (for read-write)
	\end{verbatim}
	
	The read-only API accepted GET requests and rejected non-GET requests, while the read-write API retained the original behaviour, rejecting only DELETE requests as specified to do so in the untouched source code. Various tests were performed, all listed in \textbf{postman/tests.txt}. 
	
	The deployment was verified using \texttt{kubectl get pods}, \texttt{kubectl describe deployment fnd-rw}, \texttt{kubectl describe deployment fnd-ro}, and the pod logs for both deployments.
	
	\subsection{Task 1(c)}
	
	\textbf{i) Least Privilege}
	
	Least Privilege is the principle where only the minimum amount of permissions necessary to perform a task are allocated to a program and/or its user.\cite{Least Privilege and More Fred B. Schneider}
	
	This setup applies Least Privilege by separating the FoodNDeliv API into two deployments: \texttt{fnd-rw} and \texttt{fnd-ro}. The \texttt{fnd-rw} deployment is used for operations that require database writes and is connected to the CNPG read-write service, while the \texttt{fnd-ro} deployment is used only for read operations and is connected to the CNPG read-only service. The cited definition is primarily exemplified through the read-only API  version. In addition to using the CNPG read-only service, it is restricted to only accept GET requests, meaning that the service has no other permissions besides those needed for its role.
	
	\textbf{ii) Handling traffic spikes}
	
	This setup handles traffic spikes mainly by separating read-only and read-write traffic. This means that a surge in read-heavy traffic can be directed to the read-only API instead of placing all traffic on the read-write API.
	
	The CNPG cluster was deployed with \texttt{instances:3}, providing one primary PostgreSQL instance and two replica instances. This further supports read-heavy workloads because read-only database traffic can be served through the CNPG read-only service, which routes to replica instances, rather than forcing all database traffic through the read-write primary instance.
	
	\textbf{iii) Availability during failures}
	
	Availability is improved because the CNPG database is deployed with multiple PostgreSQL instances rather than relying on a single database pod. The current system has one primary instance and two replica instances, so the system is not dependent on only one PostgreSQL pod remaining healthy.
	
	If the primary instance fails, CNPG can promote one of the existing replicas to become the new primary, allowing read-write database access to continue after failover. 
	
	\textbf{iv) Data Loss Prevention}
	
	Data loss prevention is achieved through both replication and restriction of DELETE operations. 
	
	Regarding replication, the CNPG cluster is deployed with one primary instance and two replica instances, so database state is not dependent on a single PostgreSQL pod. Data written to the primary is thus replicated, so if the primary pod fails, one of the replicas can be promoted and service can continue with a copy of the database state.
	
	Regarding restriction, the setup also restricts DELETE operations in both API versions. The read-only API, only accepts GET requests and therefore by nature cannot cause data loss via deletion. connects to the CNPG read-only service, \texttt{fnd-db-ro}. Therefore, it cannot be used to create, update, or delete records. The read-write API can modify data, but delete operations are also disabled due to \texttt{@RestResource(exported=false)} above the \texttt{deleteById} methods for all three Customer, Order, and Restaurant Repository files.

	\subsection{Task 2(b)}
	
	The Restricted Profile raises the level of isolation beyond the Baseline Profile by enforcing stricter container hardening rules on top of the Baseline policy. It has various additional controls: some new ones, and some which build upon the previous controls in baseline.
	
	
	\textbf{Volume types:} \\
	The volume type control builds upon the Baseline restriction on \texttt{hostPath} volumes. Baseline prevents pods from mounting arbitrary files or directories from the host filesystem through \texttt{hostPath}. Restricted goes further by limiting pods to a small set of approved Kubernetes-managed volume types, such as \texttt{configMap}, and others listed on the Kubernetes documentation\cite{kubernetes documentation}. This improves isolation by ensuring that storage access remains within controlled Kubernetes volume types.\\
	
	\textbf{Privilege escalation:}\\
	The privilege escalation control builds upon the Baseline restriction on privileged containers. Baseline is preventive at admission time because it stops containers from being launched with \texttt{securityContext.privileged: true}, which blocks the most unrestricted form of container execution before the pod is deployed. Restricted goes further by requiring \texttt{allowPrivilegeEscalation: false}, withholding from the pod's ability to gain that privilege later on in its lifetime. This improves isolation because if the pod is compromised, the attacker remains limited to the privileges of the compromised process rather than being able to escalate further inside the container.
	
	\textbf{Running as Non-root:}\\
	\texttt{runAsNonRoot} is the Restricted-Policy specific requirement that the container must not run as root, while \texttt{runAsUser} is the specific Linux user ID selected for the container process. Restricted policy uses both controls so that a pod must declare non-root execution and must not explicitly set the user ID 0, which is the root user. This raises isolation because a compromised process has fewer permissions inside the container than it would have if it were running as root.
	
	\textbf{Seccomp:}\\
	The seccomp control builds directly upon the Baseline seccomp rule. Seccomp limits the system calls that a container process can make to the Linux kernel. Baseline prevents a pod from explicitly setting seccomp to \texttt{Unconfined}, which blocks deliberately disabling system call filtering. However, Baseline may still allow the seccomp profile to be unset. Restricted is stricter because it requires the pod or container to explicitly use either \texttt{RuntimeDefault} or \texttt{Localhost}. Restricted requires an allowed seccomp profile to be declared. This improves isolation because if the container is compromised, the attacker has fewer system-calls available for post-exploitation.
	
	\textbf{Capabilities:}\\
	The capabilities control also builds directly upon the Baseline capabilities rule. Baseline restricts which additional Linux capabilities may be added to a container. Restricted, on the other hand is stricter because it requires containers to drop all capabilities and only allows \texttt{NET\_BIND\_SERVICE} to be added back; thus only allowing the capabilitiy of  binding a server socket to a privileged port\cite{Implementing the Principle of Least Privilege Using Linux Capabilities: Challenges and Perspectives}
